# UX Review — Home CCTV Hub

**Product:** Home CCTV Hub — local CCTV operator console (Next.js 16 App Router, React 19, Tailwind v4), "Sentinel" dark operator theme
**Reviewer:** Agent 1, independent UX critic (read-only audit)
**Date:** 2026-11-04 (Asia/Kolkata)
**Environment:** running dev build at `http://localhost:3000` (local hub, logged in as the ADMIN account in `.env`)
**Verdict:** a well-executed operator console with a strong accessibility baseline, dragged down by a contradictory system-health signal, a broken date/filter commit model on Events, an invisible unread lifecycle, and focus-management gaps in overlays and focus mode. **6.5 / 10** (see §6).

> A floating circular "N" bottom-left in screenshots is the Next.js dev indicator, not application UI; it is ignored throughout. `audit/screenshots/capture-metrics.json` records 68/68 captures HTTP 200 with zero console errors, and my independent runtime sweep reproduced zero console errors on all 15 signed-in routes.

---

## 1. Scope and method

### 1.1 Scope

All 17 routes were judged in their **current running state** (no redesign proposal):

- Public: `/login`
- Signed-in (ADMIN): `/` (dashboard live view), `/playback`, `/events`, `/events/[id]`, `/events/stats`, `/faces`, `/notifications`, `/cameras` (Camera setup), `/device`, `/account`
- ADMIN-only: `/settings` and `/settings/{users,notifications,detection,audit-log,system}`

Focus areas: navigation and discoverability; end-to-end workflows; information hierarchy and density; interaction complexity; WCAG 2.2 AA accessibility; usability, error/empty/loading states.

### 1.2 Method

1. **Evidence-set review** of the lead-captured screenshots and metrics (E1–E4 below): every route at four viewports plus full-page and interaction states.
2. **Source reading** of `src/components/**` and `src/app/**` for the mechanisms behind each observation (E5), with `file:line` references so claims are re-checkable.
3. **Independent read-only runtime probes** with Playwright/Chromium (E6): 1440×900 `en-IN` desktop and 390×844 touch mobile contexts, authenticated via `POST /api/auth/login` with a reused cookie. Probes performed: tab-order walks, skip-link activation, focus-mode entry/exit, opening the mobile More sheet and Events bottom sheet, opening the playback date popover, changing (not submitting) filter selects while recording network calls, and one deliberately failed sign-in to inspect the error treatment. **No** save, delete, user creation, test notification, password change, or mark-read API call was made; no application files were modified.
4. **Authenticated GET checks** of `/api/events`, `/api/system/health`, `/api/dvr/status` (E7) to corroborate what the UI displays.
5. Cross-checked the running UI against the values in the capture metrics rather than trusting either alone.

Helper probes live at `/tmp/ux-probe.cjs`, `/tmp/ux-probe2.cjs`, `/tmp/ux-probe3.cjs` with outputs `/tmp/ux-runtime.json`, `/tmp/ux-runtime2.json` (outside the repo by design).

### 1.4 Limits of this evidence

Target-size metrics (E4) measure an interactive element's own bounding box; a `<label>` wrapping a control can enlarge the effective hit area, and WCAG 2.5.8's spacing exception was not algorithmically evaluated (see §3.3). Screen-reader speech, 200 % zoom/reflow, 320 px width, forced colours, non-Chromium engines, and the VIEWER role were not exercised (§7).

### 3.3 Target-size caveat (honesty note)

WCAG 2.5.8 allows an undersized target when a 24 px-diameter circle centred on it does not intersect another target's circle. Many of the measured 17–18 px card links sit alone inside cards and may satisfy that exception; the 15×15 checkboxes are isolated on the right of their rows. I therefore report target size as an **AA risk requiring per-component judgement**, not as a confirmed blanket failure. The 44 px figures are best-practice/touch guidance, not an AA requirement.

## 5. Strengths to preserve

1. **Live-video-first dashboard.** At 1440×900/1920×1080 the 4:3 live wall is the dominant element, fits above the fold, with a `4 of 4 streams live` pill and per-camera ONLINE status. KPI strip and right rail are secondary. This is the right hierarchy for a CCTV console, and it survives tablet/phone by stacking without horizontal overflow.
2. **Navigation structure that mostly scales.** Grouped sidebar (Monitor/Security/System) with a persistent Settings sub-nav, an active-indicator rail, mobile 5-item bottom bar + More sheet, and a genuine breadcrumb on event detail. Every signed-in route is reachable without a dead end; the ADMIN-only Settings item is filtered out of the navigation for viewers by code (`AppShell.tsx:225,391`; runtime unverified — §7).
3. **Accessibility baseline.** Skip link that actually works, visible 2 px focus rings, zero unnamed controls/inputs on 15 routes, `aria-current`/`aria-pressed`/`aria-expanded`/`role="switch"`, `role="alert"` errors, `role="status"` saves, `lang="en"`, reduced-motion support, and no horizontal overflow at any of the 68 captures.
4. **Colour system that passes.** Semantic text contrast measured 5.44–17.27:1; statuses never rely on colour alone; a coherent Sentinel palette (teal accent, green online, amber warn, red danger) used consistently across badges, bars and lamps.
5. **Honest, well-written states.** Every data surface has a loading skeleton, an `EmptyState` with title + explanation + action, an `ErrorBanner` with retry, and plain-language microcopy ("Today's recordings load on open", "Static preview — live video plays on the Dashboard", "no frame leaves this LAN", "Every face stays Unassigned until a later phase adds people"). Snapshot fallbacks say "Snapshot not available" instead of inventing data.
6. **Destructive-action care in admin.** Delete user/rule use `role="alertdialog"`, "this cannot be undone", and Escape-to-dismiss; the detection page has a **sticky Save bar** that sits above the mobile bottom nav.
7. **Login page.** Split local-first value proposition + form; correct labels/autocomplete; failure is announced and focused; no credential in URL (native POST path).
